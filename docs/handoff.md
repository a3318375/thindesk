# 接手状态与验证方法

核对日期：2026-11-21。动态连接状态、进程版本和测试数量应重新核查，不以本页替代现场结果。

## 已确认的方向

- ThinDesk 是个人内网 Agent Web 工作台；Codex 和 Pi 都是真实运行器。
- UI 已结束 DSH 复刻阶段，使用 assistant-ui。保持当前布局，重用官方 Elements；不重新引入 DSH 模块系统、Lobe UI 或旧预览目录。
- 近期只实现运行器给出的本轮差异。Pi 不装 diff 插件；不追踪所有 shell／write 修改，不提供假撤销。
- QQ 联调暂停。微信暂不测试。已有授权不代表可以在无关开发中向 IM 发测试消息。

## IM 接手状态

「个人助手」使用固定会话 ID `personal-assistant`。默认工作目录为 `$THINDESK_DATA/personal-assistant`，可通过 `THINDESK_PERSONAL_DIR` 指定。首次打开或收到消息时创建，不登记到项目列表。旧项目对话保留在原处。个人助手沿用全局守则，本次没有创建专属提示词或修改运维手册。

设置中的 IM 仅配置渠道连接。QQ、微信和 Telegram 入站及网页共用队列、运行器和同一份历史；回复跟随该轮入站路由和原消息上下文，网页轮次不投递。混合来源不能合并到一个 IM 轮次，输入中提示及 /stop 也仅适用于发起该轮的聊天。升级时旧同步规则下未完成的投递标为已取消。历史路由在下一条来信时转向个人助手。服务端保留现有机器人启用状态。

真实 QQ 出站已验证，QQ 入站及自动回答仍待验证。检查连接时只读取服务端白名单字段。

三渠道收发、附件、去重、恢复和按来源回复已有本地协议替身测试；通过替身不代表真实账号权限和平台限制已验证。设置 → IM 机器人 → QQ／微信 → 扫码登录，在手机授权后保存凭据并启动个人助手渠道。微信要求配对码时在弹窗输入，遇到二维码过期可重新生成。连接情况以渠道状态为准。Telegram 使用 BotFather Token。扫码仅用本地替身验证，未用真实账号重新授权。

## 开发与运行

| 项目 | 值 |
| --- | --- |
| 工作目录 | 项目检出目录 |
| 入口 | 本地默认为 `http://127.0.0.1:3781/`，部署时使用配置的监听地址 |
| 服务 | `thindesk.service`，由部署用户运行 |
| 数据库 | `~/.local/share/thindesk/workspace.sqlite` |
| Pi 原生会话 | 数据目录下 `pi-sessions/` |
| Codex 原生状态 | `CODEX_HOME` 或 `~/.codex/` |
| 测试示例 | 测试夹具单独注入；生产工作台不自动生成示例。保留旧库中曾用示例路径执行的会话的目录兼容逻辑 |
| 研究／截图／备份 | `~/.local/state/thindesk/`，不属于源码依赖 |
| 代码版本管理 | Git，默认分支为 `main` |

`npm run build` 同时执行 strict TypeScript 检查和 Vite 构建。`npm test` 启动临时 SQLite、服务、独立运行器和 Chromium，使用 `tests/fixtures/codex.mjs`／`pi.mjs` 替代真实运行器。IM 测试使用本地 HTTP 与 QQ SDK 替身，不访问账号。

常用验证：

```bash
npm run build
npm test
node --test --test-name-pattern='活动动画|JSONL' tests/e2e/workbench.test.mjs
node --test tests/e2e/insights.test.mjs
node --test tests/e2e/im.test.mjs tests/e2e/im-adapters.test.mjs tests/e2e/im-integration.test.mjs
```

后两组中的 IM 测试也只访问本地替身。运行 `npm run test:visual` 则访问真实 Web；确认测试代码不会提交真实消息后再使用。

生产绑定 LAN 地址，`curl http://127.0.0.1:3781/` 可能拒绝连接；使用实际地址。不要据此判断服务已停。

## 重新部署与保护数据

1. 先读系统运维知识手册；确认 `systemctl show thindesk.service -p MainPID` 和 `/proc/self/cgroup`。
2. 构建通过，按改动完成测试；备份需要改写的数据，用 SQLite backup API 获取一致副本，避免只复制正在写入的主文件而遗漏 WAL。首次升级分表存储前必须备份；旧版代码不能直接读取 storageVersion=2 的元数据，回滚需要恢复升级前数据库。
3. 静态文件从 `dist/` 提供；后端 TS 变更需要重载 Node 服务。
4. 如果自己属于 thindesk.service，不直接重启。使用服务外的 systemd transient worker，等待所有 session 无 running、无未暂停队列，并再次确认空闲后重载；重载后检查 HTTP 和服务日志。
5. 不把任何渠道凭据写进项目文档或输出。尤其不要直接打印 cc-connect 管理状态原文，它可能含 token。

前一轮差异功能和本轮审查若连续进行，独立空闲重载 worker 可能仍在等待当前回答结束。检查其状态，不重复排多个重启；不能在没有结果时声称后端已加载最新版。

## 后续边界

用户已授权并实施提问、审批、长会话存储优化、运行恢复及逐模型思考强度。文件工作台、Git、自动化暂不扩展；用户明确不希望产品变成 IDE。剩余内容需要后续讨论：

1. 大规模历史：服务启动仍加载历史入内存，统计／全文导出仍有全量成本；继续以测量决定是否下推检索和真正的数据库分页。
2. 上下文压缩由 CLI 决定；页面显示原生压缩事件。
3. 机器／worker 本身故障后的恢复不是原地接管，当前明确中断并允许手动继续，不盲目重放外部操作。
4. 历史编辑和原生分支树已取消。IM 实机验证继续暂停。

接手后先读取本页、架构和最近审查；再检查构建、现有测试和待重载状态，通常无需重读全部历史聊天。

模型恢复、分段控件和队列回归的验证范围见审查记录。


## Codex 子代理和会话来源

Codex 会话的「＋ → 委托子任务」或 `/delegate` 打开任务表单。用户可沿用 CLI 的子代理配置，也可从 Codex 模型目录选一个模型。表单将委托写入草稿，发送沿用当前会话队列，主模型负责调用原生委托工具。只有收到运行器事件才出现任务卡。一个子线程对应一张默认收起的 assistant-ui Task Card，可以分别展开查看委托和回报。多项并行时各自更新状态。

项目列表和最近会话按创建来源显示图标。网页会话使用 Lucide 地球，IM 会话使用渠道标志，在网页中续聊沿用原来源。从网页委托到刷新恢复已通过浏览器与协议替身回归；真实模型派发和返回结果仍需联调。协议用例在 `tests/e2e/subagents.test.mjs`。
